最近我有一个很真实的学习痛点：看 B 站课程视频时，我并不喜欢一边看一边做笔记。

一方面，做笔记会打断观看节奏；另一方面，很多课程视频信息密度很高，看完以后又很难快速回顾重点。所以我想到一个需求：

> 能不能只提供一个 B 站视频链接，让工具自动提取视频内容，并帮我整理成学习笔记？

于是我让 Codex 帮我做了一个本地网站。它的功能很简单：输入 B 站视频链接，自动提取视频内容，然后生成 Markdown 学习笔记。

<!--more-->

从最终效果来看，它背后主要依赖这几类技术：

```text
B站接口：拿视频信息、字幕、音频
ffmpeg：处理音频格式
faster-whisper：把声音转成文字
大模型：把文字整理成知识结构
React + Express：做成本地可用的网站工具
```

## 这个工具大概是怎么工作的？

它并不是“AI 直接看懂视频”。

更准确地说，它走的是一条很实用的路线：

```text
B站视频链接
  -> 获取视频信息
  -> 优先读取字幕
  -> 没有字幕就提取音频
  -> 用本地 Whisper 把音频转成文字
  -> 再让大模型把文字整理成笔记
```

所以真正关键的一步是：

> 先把视频变成文本，再让 AI 总结文本。

视频本身对程序来说并不好理解，但一旦变成文字，后面的摘要、提炼重点、解释术语、生成复习问题，就都是大模型擅长的事情了。

## 前端和后端分别是什么？

这个项目做成了一个本地网站。它有两个部分：前端和后端。

简单理解：

```text
前端：用户看得见、点得到的界面
后端：藏在后台、负责干活的程序
```

前端是一个 React 小应用。

这里的“React 小应用”可以理解为：

> 一个用 React 框架写出来的、规模不大、功能比较单一的网页界面程序。

它负责：

- 显示输入框
- 显示按钮
- 让用户输入 B 站链接
- 展示生成后的 Markdown 笔记
- 提供复制和下载功能

后端是一个本地 Express 服务。

Express 是 Node.js 里非常常用的后端框架。可以把它理解成后端开发的“基础脚手架”。

它负责：

- 接收前端发来的请求
- 解析 B 站链接
- 获取视频字幕或音频
- 调用本地 Whisper 转写
- 调用大模型生成总结
- 把结果返回给前端

一个类比是：

> 前端像餐厅的点餐界面，后端像厨房。用户点了“生成笔记”，前端把请求送到后端，后端真正去处理视频、转文字、生成总结，最后把成品端回来。

## 什么是本地服务？

这个工具目前运行在我自己的电脑上，而不是部署到云服务器。

也就是说，后端启动后，会监听一个本地地址，比如：

```text
http://127.0.0.1:8787
```

前端页面可能跑在：

```text
http://127.0.0.1:5173
```

这两个地址里的 `127.0.0.1` 或 `localhost`，都表示“当前这台电脑”。

本地服务的好处是：

- 不需要买服务器
- 不需要配置域名
- 开发调试方便
- 改完代码可以立刻看到效果
- 音频转写可以在本机完成，隐私更可控

局限也很明显：

- 关掉电脑或服务，工具就不能用了
- 别人不能直接访问
- 如果要公开给别人用，还需要部署到真正的服务器上

## B站内容是怎么拿到的？

用户输入一个 B 站链接后，后端会先解析出视频的 BV 号。

然后它会尝试获取视频信息，比如：

- 视频标题
- UP 主
- 分 P 信息
- 视频对应的 cid
- 字幕列表
- 音频流地址

如果视频有公开字幕，工具会优先使用字幕。因为字幕本身就是文字，处理速度最快。

但很多视频没有公开字幕，或者字幕接口拿不到。这时候就需要走第二条路：

```text
提取音频 -> 本地语音识别 -> 得到文本
```

这也是这个项目真正有用的地方。

## ffmpeg 负责什么？

ffmpeg 是一个非常强大的音视频处理工具。

在这个项目里，它主要负责把从 B 站拿到的音频流转换成适合转写模型处理的音频格式。

可以简单理解为：

> B 站给你的音频不一定是 Whisper 最喜欢的格式，所以先用 ffmpeg 把它“整理干净”。

它就像一个音视频格式转换器，把原始音频处理成后续模型更容易识别的形式。

## 本地 Whisper 是怎么把声音转成文字的？

这个项目使用的是 `faster-whisper`。

Whisper 是 OpenAI 开源的语音识别模型，可以把语音转换成文字。`faster-whisper` 则是一个优化版本，速度更快、资源占用更低，更适合在普通电脑上本地运行。

它的工作流程大致可以理解为四步：

1. 预处理音频
   把音频统一成模型容易处理的格式，并提取声音特征。

2. 编码器分析声音
   模型会分析声音中的语音特征，比如发音、节奏、上下文。

3. 解码器生成文字
   模型根据声音特征，一个词一个词地预测出对应文本。

4. 输出分段和时间戳
   最终得到类似这样的结果：

```json
{
  "from": 12.3,
  "to": 18.6,
  "content": "互联网访问网页，本质上是浏览器去请求服务器上的资源。"
}
```

这些分段文本会继续交给大模型整理成学习笔记。

## 为什么要用本地 Whisper？

一开始我尝试用中转站的音频转写接口，但发现它不支持 `/audio/transcriptions`，会出现连接失败。

所以后来换成了本地 Whisper。

这样做的好处是：

- 不依赖中转站是否支持音频上传
- 不用额外支付音频转写 API 费用
- 音频转文字在本机完成，隐私更好
- 只需要把转写后的文本交给大模型总结

当然，它也有代价：

- 第一次需要下载模型
- 长视频转写会花时间
- CPU 运行速度不如云端 GPU
- 转写质量会受音频清晰度影响

但对个人学习场景来说，这个方案已经很实用了。

## 大模型负责什么？

Whisper 只是把声音变成文字。

真正把内容整理成“笔记”的，是大模型。

它会接收一大段带时间戳的视频文本，然后根据提示词生成结构化 Markdown。

目前我比较喜欢类似 BiliGPT 的“全文总结”风格，所以输出结构大概是：

```md
# 视频标题

## 摘要
一段高密度总结

## 亮点
- 💻 ...
- 🌐 ...
- 🚪 ...

#标签 #标签 #标签

## 思考
问题 + 回答

## 术语解释
术语: 解释

## 时间线
- [00:00-01:30] 主题
```

这种格式比逐段笔记更适合快速复习。

它不会把每一分钟都展开讲，而是帮我提炼：

- 这节课讲了什么
- 哪些知识点最重要
- 有哪些核心概念
- 有哪些值得思考的问题
- 之后怎么快速回顾

## 这个工具的本质

如果用一句话总结：

> 这个项目的本质，是把“看视频做笔记”拆成了几个自动化步骤：提取内容、转成文字、理解结构、生成笔记。

它背后不是单一技术，而是一组工具协作：

```text
React：做用户界面
Express：做本地后端服务
B站接口：获取视频信息和音频
ffmpeg：处理音频格式
faster-whisper：本地语音转文字
大模型：总结、提炼、生成 Markdown
```

我最喜欢的一点是，它没有强迫我改变学习习惯。

我还是可以正常看视频。

但当我需要复习、整理、回顾时，只要把视频链接丢进去，它就能帮我生成一份结构化笔记。

这对我来说，比单纯收藏视频有用得多。
